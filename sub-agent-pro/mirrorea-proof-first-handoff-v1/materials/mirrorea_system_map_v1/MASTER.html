1. この文書が整理する全体像

中心目標は、意味のある計算・状態・関係・作用を記述すると、配置と連携が導かれ、検証・観測でき、稼働後も構成を追加・変更・撤去しながら使い続けられる基盤を作ることです。

並列計算、Webサービス、シンクライアント、対等な分散サーバ、VR、SNSは、別々のCoreを必要とする独立した目標ではありません。同じ構成原理が、異なる配置・時間・主体・提示に適用できるかを試す利用領域です。仮想空間は三次元幾何に限定せず、対象・関係・主体・作用が存在する計算上の環境として捉えます。[U01,U08,U12,U13]

2. 変えない目標と、決めていないこと

2.1 成功の中心

成功は、(a) 意図を一体として記述できる、(b) 実現上の分割を変えても必要な意味を保てる、(c) 結果・失敗・未確定を正しく把握できる、(d) 他の構成を安全に接続できる、(e) 動作を継続しながら進化できる、という能力で判断します。

「やりたいことを書けば動く」は、未指定の意味を推測して常に成功させることではありません。readの一貫性、作用の権限、許される失敗等は、必要なら契約・宣言・注釈で与えます。機構の手書きは減らし、意味の曖昧さは残さない方針です。[U01,U02,U05,R2]

「無制限に進化する」は、将来の用途や構成数を初期に固定列挙せず、受理条件を満たす追加へ進めることです。任意の変更の無条件受理、有限機器の無限資源、すべての故障での無停止を意味しません。旧版の撤去・履歴の回収まで含めて継続性を扱います。[U14]

2.2 非目標と、未採用の方式

OSや物理network stackの全面再実装、単一consensus、単一game engine、特定UI・特定URL形式は、今回の中心ではありません。World/Avatar/Room/Page等をCoreへ入れません。PrismCascadeとTyped-Effect Wiring Platformは独立した接続先であり、同時完成を要求しません。[R1,R5]

同時に、F0.2の次の選択も要件へ固定しません。参照ごとのowner snapshot、loop-free owner body、第一階のみ、public-only actor、明示2PC型activation、Prepared時点からの権限予約、多項式certificateだけ、新instanceへのimport。これらは候補の前提です。異なる意味を選ぶなら、それに依存する証明と実現を変えます。[F2]

通信IFを先に書かないことは、独立したmodule間の意味契約まで無くすことではありません。 一つのシステム内部はchecked meaningから生成し、独立したシステム間は、要求・提供契約と必要な証拠で接続します。全世界のsourceを一度に集める設計は前提にしません。[U01,U13,D:WW-01]

全責任を一つのプロセスや同じDBへ置く要求ではありません。数学的に同じ対象を指すことと、物理的に中央集約することは別です。検証・権限・観測は縦積みの一段ではなく、複数の境界を通過する情報に条件を与えます。

4.1 通常の実行経路

普通のsource＋意味上必要な宣言
  → parse / scope / type / contract / local-theory checking
  → checked meaning＋未解消義務＋source対応
      ├─ 純粋なprojection → locus別artifact / 生成された効果・通信計画
      └─ 証拠検査・必要なobligationの解消 → 保持すべき保証と前提
  → 両経路のidentityと契約を照合したactivation / 現在policyでのadmission
  → 非権威的なphysical bindingと、使用時にも再検査する実行
  → state/result/failure/unknown と実際のoccurrence
  → observer条件を満たす情報projection
  → View / debugger / headless consumer

この図は必ず全計算を起動前に一括検査する手順ではありません。静的に決められる条件、接続時条件、使用時条件、履歴を通じて監視する条件を分けます。配置別成果物の純粋な生成・検査と、それを実行してよいという判断も別です。未解消義務を持つ成果物は計画や診断として調べられても、それによって実行許可を得るわけではありません。physical bindingの準備位置は実装裁量ですが、どの順序でも権限や意味を発明してはいけません。

「未宣言通信を作らない」は、暗号handshakeやACK等のすべてを日常sourceへ書く要求ではありません。意味上のデータ移動、権限、失敗、情報公開への影響が、定義した実現境界に対応し、無根拠に増えないことを要求します。[R2]

4.2 進化の経路

既存構成＋変更source＋必要な契約/移行/証拠
  → 追加・交換・撤去等の分類
  → 依存と完全な影響範囲の検査
  → 現在の権限と利用側契約の確認
  → 準備・未完了処理の処置・必要範囲の停止
  → profileに従う確定判断とactivation
  → 新しいcode/state/関係/権限世代/証拠への対応
  → 許可された観測・保存・旧資源の回収

拒否と延期は、所定の診断・監査・資源使用を除いて意味状態を変更しません。ただし、既に外界へ作用した失敗まで「無変更」として扱うことはできません。受理前、実行開始後、確定後、応答前後で条件を分けます。

4.3 境界に共通して保持する情報

意味上必要な範囲で、対象のidentity/incarnation、code/contract/theory/policyの版、要求と結果の対応、主体、作用範囲、時間・frontier、効果/失敗、観測許可、資源条件、証拠の前提を保持します。これを一つの固定wire schemaへ決めることはしません。hashは照合の手段であり、発行元の真正性や権限そのものではありません。

個々のDAGの非循環性を足しても、全体系が健全とは限りません。例えばpatchの撤去は存在を変え、関係を無効化し、再取得の権限を変え、保存と観測の前提にも影響します。これらを同じ構成の遷移として扱います。

F0.1の反例では、別々には安全な辺追加が合成後に循環を作りました。rank証拠は一つの十分条件ですが、唯一の実装方式にしません。完全な依存追跡と保守的再検査も候補です。[F1,F2]

また、同じlineageのfallback単調性は、時間越しの普通の状態変更まで単調にする要請ではありません。長命な候補の存在は、常時通信可能であること・型が適合すること・write権限があることを意味しません。

6.2 目標命題の型

以下は本書で新たに証明した命題ではなく、検証義務の形です。

受理された操作の保存。 型・依存・権限・証拠・履歴の整合を表す WF を、実行と変更の具体的規則について保存します。

WF(C)\land Step(C,a,C')\land EnvOK(a,C)\implies WF(C').

Stepを「WFを保存するもの」とだけ定義して証明を終えてはいけません。検査・遷移を先に具体化して示します。仮定を破る外界入力には、拒否・不確定・障害境界を設け、実現が仮定に依存する箇所を明示します。

実装との対応。 source/abstract状態と実装状態の関係を定義し、実装の内部step、失敗、作用が抽象意味へ対応することを示します。停止し続ける実装を排除するには別の進行条件が必要です。秘密については二実行またはhyperpropertyの保存を別に扱います。[W6,W8]

相対完全性。 選択した宣言体系で導出できるprogramについて、許されたannotationを伴う検査が受理することを目標にします。証明付き境界では、未解消義務の解消方法も必要です。「全部Unknownへ送れる」だけでは表現力も実行可能性も達成しません。

進化。 受理された追加・交換・撤去等が同じWFと存続契約を保つなら、任意有限回の進化にもその保存を広げます。無期限運用のlivenessやstorage上界は、この帰納法だけからは従いません。

7. 使いやすさを判定可能にする

使いやすさを「構文を後で短くすること」に限定しません。次の能力を、正しさと同じ受入れコーパスで確認します。

重複記述の少なさ。 同じ意図のために、node別logicと通信仕様、別の認可表、別の可視化モデルを手で同期しない。必要なmeaning contractは一度定義し、その参照を利用します。

段階的な理解。 普通のsourceから始め、必要時にgenerated plan、依存、policy、証拠、実行へ降りられる。内部機構を永久に隠すのではなく、普段は背負わせず、必要時は追えることを求めます。

意味のある拒否。 source span、破れた条件、対象/版、修正すべき範囲を示す。機密性のために理由を隠す場合は、その非公開性を正しく表示します。攻撃者へ秘密を明かす詳細errorは要求しません。

未知と制限の明示。 型不適合、proof未解消、unsupported profile、権限なし、結果不明を区別します。便利さのためにUnknownを成功へ変えませんが、全拒否で目的達成ともしません。

独立した作者による再構成。 runtime内部を変更しない別作者が、文書とsourceから新しい正例を作れることを評価します。完全ノーコードUI、特定のnotation、全情報のGUI編集は初期αの既定条件ではありません。[U02,U05,U07,U15]

性能の数値目標はQ-30で決めます。測定項目には、annotation量、重複したmeaning記述数、診断から原因へ到達する手順、検査時間、変更影響範囲、観測負荷、session復旧手順を含めます。ここで恣意的な数値を合格基準として固定しません。

8. 最も重要な統合受入れの場面

SC-24は、機能の足し算ではなく、同じ構成に対する縦断的な受入れです。 基礎にWorld/Avatarを入れず、構成Xとその上の拡張Yとして定義します。

  1. XをA/B/Cへ展開し、source由来の計算と関係を操作します。
  2. 別作者が、局所理論で一部を強く検証したYを、A/Cへ追加します。必要な権限は別に認可します。
  3. Yは短命な参加者側の対象へ関係を持ち、長命側へfallbackする契約を持ちます。存在/admission/patchの対応を検査します。
  4. 二層の認証・認可条件で操作を許可します。証明だけ、異なる主体の二つの許可、古い世代は拒否します。
  5. sample gap、意味上退出、失効、lost replyを別々に発生させます。意味状態と提示状態、実行事実と要求元の知識を混同しません。
  6. 正当なY更新を適用し、不正なwriterや互換性を壊す更新を拒否します。独立した活動は必要以上に止めません。
  7. 利用する全componentを保存契約へ参加させ、選択した復旧方式で再開します。旧権限を無断復活させません。
  8. 同じ構成仕様から、定義した公開入力・環境・schedulerの対応条件を満たす比較実行を作ります。観測ON/OFF、observer失効、秘密の差に対して、宣言した非干渉・忠実性・資源条件を確認します。一つの実行だけから二実行の性質を結論せず、比較のために別の実装系や期待traceを持ち込むこともしません。

この一例の実行成功だけで一般定理が得られるわけではありません。反対に、一般定理だけで実際の構築・利用経路が使えるとも限りません。一般命題、対応実装、正例と反例、利用者の手順の四つを同じIDで結ぶことが受理条件です。

9. αの範囲と、その先

αは「すべての将来機能を持つ」ことではありません。しかし、本来の使い方の根幹を、試験用helperや他言語のdomain logicへ逃がして完成扱いすることもできません。[U15,U17]

αで限定しやすいものは、対応host/OS、transport、renderer、初期の数値型、認証方式の種類、局所理論の種類、更新方式、cluster規模、可用性profileです。ただし、その限定が何を保証し何を除外するかを明記します。

αでも隠してはいけない不足は、sourceから新しい普通の構成を作れないこと、参加を構成として扱えないこと、全componentの保存対象が不明なこと、private観測をpublic-only定理で代用すること、証拠と権限を混同することです。

任意の理論loaderや完全な高階言語をαに一括要求はしません。一方、理論を局所化して境界で接続する構成原理を、少なくとも選んだ異質な具体例で示します。同様に、認証方式を何十種類も作る必要はありませんが、複数層が同じ要求へ正しく合成される代表profileを定めます。この最低代表性は、今回の意図から導いたα案であり、正式な採用は未決です。

16. 保証・証明の達成対象

以下は本整理で新たに証明した結果ではありません。既存のTHM/OBLとF0.xを照合し、何をもって基礎が成立したと扱うかを示す目標です。全てを同じ証拠手法で示す必要はありませんが、上位が依存する保証は未解消のまま成功扱いにしません。

PT-01 — 表現力と宣言的規則

対象： 指定した利用能力を、例固有のruntime拡張なしに表現する。

必要な根拠： 代表コーパス・反例・構文/意味の定義。これは定理だけでは代替しない。

区別するもの： Turing完全性だけ、全拒否体系への完全性だけでは不十分。

PT-02 — checkerの健全性・相対完全性

対象： 型導出、注釈、検査結果、残余義務の対応と、選択断片での終了を示す。

必要な根拠： 宣言的規則とalgorithmic規則の機械検査を目標にする。

区別するもの： 任意の意味的真理の自動証明、programの無条件終了は要求しない。

PT-03 — sourceから分散実行への対応

対象： 生成物と実行stepがsourceで許された意味へ対応し、未宣言作用を増やさない。

必要な根拠： 構造/step simulation、source/Core/artifact束縛、実backend refinement。

区別するもの： trace包含だけから情報流や無条件進行を推論しない。

PT-04 — 多種グラフの保存

対象： 存在・関係・参加・patchの各意味と、グラフ間の使用条件を全変更で保存する。

必要な根拠： 具体的な遷移定義と同一Configについての保存証明。

区別するもの： 個別DAGのcycle検査の合算は全体証明ではない。

PT-05 — 参照・寿命・fallback

対象： 有効な候補のみ使用し、意味上の失効で正しい代替/失敗へ進み、旧世代は復活しない。

必要な根拠： 一般有限chain、権限使用点、reparent/leave/reacquireの統合。

区別するもの： 長寿命であることを常時到達や任意write許可としない。

PT-06 — 関係射影と時間

対象： 同じ契約上の入力文脈で、関係を保持した射影/評価が指定の対応と誤差を満たす。

必要な根拠： 時間域・sample適合・依存labelを含む定理とrenderer adapter試験。

区別するもの： no-split-frame等を完全なclock同期と同一視しない。

PT-07 — 並行実行の安全性

対象： owner coherence、競合・依存順序、要求/結果/継続の対応を許容scheduleで保つ。

必要な根拠： 実行と通信の関係、失敗matrix、scheduler仮定を限定した証明。

区別するもの： race-freeだけで全順序・共同不変条件を得ない。

PT-08 — 進行性・資源

対象： 存在的な完了経路と、公平性仮定下の全実行の進行を区別し、資源不足の意味を示す。

必要な根拠： schedule前提、ranking/公平性、上限・拒否・回収の検証。

区別するもの： 無条件liveness、無限資源、平均性能を最悪保証にしない。

PT-09 — 効果境界の保存

対象： handler/provider/FFIが、宣言された型・失敗・権限・継続使用・外界不確定性を保存する。

必要な根拠： handler law、adapter refinement、Started前後crash反例。

区別するもの： rollbackが外界を消す、任意効果のexactly-onceを仮定しない。

PT-10 — 認証・認可層の合成

対象： 同じ主体・要求・版を対象に、信頼・委譲・層変換が承認された許可を越えない。

必要な根拠： 資格証拠→主体→policy→grant→useの対応と層の合成証明。

区別するもの： 命題の証明から政治的/運用上の信頼先を自動決定しない。

PT-11 — 現在性・失効

対象： code/contract/resource/grantの世代を保ち、queued/in-flight/patch/replayの旧使用を拒否する。

必要な根拠： 同時変更と使用点のlinearization、reservation policy別の証明。

区別するもの： 既実行を失効で無かったことにしない。

PT-12 — 局所理論と契約の合成

対象： 局所仮定の輸出、値・資源の変換、環境干渉、全mutator閉包を共通意味で保存する。

必要な根拠： 異質な二つ以上の具体的理論と境界checkerの証明・反例。

区別するもの： 未定義のSafeExtensionを仮定しただけでloader完成としない。

PT-13 — 交換と受理された進化

対象： 保存契約・成功範囲・状態関係・依存先を満たす変更が、実行中も基礎不変条件を保存する。

必要な根拠： 追加/撤去/移行/契約更新の規則、具体checkからの保存定理。

区別するもの： 拒否時非更新のみを受理patchの安全性としない。

PT-14 — 分散activationと局所性

対象： 準備・確定・適用・停止の内部stepが選択した抽象変更へ対応し、他の独立活動を壊さない。

必要な根拠： 完全footprintの根拠、fence所有、crash状態とdecisionの証明。

区別するもの： 2PC採用や即時失効の意味を暗黙固定しない。

PT-15 — 観測忠実性と受動観測の非干渉

対象： 表示事実は実行から導かれ、受動観測を除いた振る舞いが定めた同値を保つ。

必要な根拠： observer projectionとerase関係、同環境条件での比較。

区別するもの： ゼロ物理負荷、能動debuggerの無害性を主張しない。

PT-16 — cut・復旧・非復活

対象： 必要な全成分・全依存が保存され、採用した復旧種別で状態・履歴・現在制御の条件を保つ。

必要な根拠： checkpoint入力完全性、Z-path適用条件、host prefix契約、全成分復元試験。

区別するもの： 型が合うarchiveを真正な履歴と同一視しない。

PT-17 — 統合と任意有限進化

対象： 共通の前提を満たす実行・参加・変更・復旧の各stepの保存から任意有限prefixの保証を得る。

必要な根拠： 同じ状態・版・権限・環境を使う補題の接続図と非空な統合例。

区別するもの： 部分モデルの集合を一つの統合定理と数えない。

PT-18 — 情報流・host・TCB

対象： 定めた観測モデルで二実行の情報流と、実装の隔離・資源契約を保証へつなぐ。

必要な根拠： relational proof、host仮定一覧、機械化/未証明実装境界、検査範囲。

区別するもの： public-onlyや単一trace proofからprivate分散安全性を導かない。
