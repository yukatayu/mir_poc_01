# 理論の受理から実装へ接続する計画

## 1. 計画の扱い

これは研究候補と受入れ条件の提案であり、Plan 250に代わる自動実行命令ではない。I3-3の有限受理を保持し、I3-4を勝手に再開しない。F0.3の実装をそのまま本番Coreへ採用する指示でもない。

「次に依存する基礎は先に閉じる」を原則にする。ただし、基礎の反例を得るための限定実装は止めない。研究の出口は、候補一覧の拡大ではなく、定義・定理・反例・具体的な実装境界である。

## 2. 推奨する全体設計

### 2.1 値と計算を分けた小さい意味コア

最終構文とは別に、純粋な値、型付きの計算、参照する環境、現在の使用条件を分ける。再帰を許すruntime計算の全域性と、型検査/証拠検査の停止性を同じ要求にしない。

最初に比較する型構成候補は、基本値、積/和、名前付き再帰データ、純粋な高階関数、計算型、現在性を持つhandle、必要な有限index/refinementである。ネットワーク越しの任意closureを一度に許すのではなく、純粋で閉じた値の移動、instance interfaceへのhandle、効果ful closureの使用条件を分ける。

これは「高階や依存型を永久に除外する」選択ではない。SL-08/TY-05を、具体的な利用例と型規則を備えた独立の研究対象として取り込むための案である。完全な依存型や様相を、単にF0.3のrecordへ別fieldを追加して導入したとしない。

### 2.2 現在性を共有する、別々の判断

型判断、局所的な証拠、現在認可、live依存、結果の消費、保存可能性が、同じ対象・世代・source・契約を参照する。これらを一つの巨大な型の中へ平坦化するのではなく、正確な文脈を共有して別々に検査する。

F0.3のsupport closureは、このうち構成の使用可能性を扱う。一般の数学的な命題やデータの意味を、単なるlive/nonliveへ還元しない。型/契約の証明は、どの環境で成立するかを別に保持する。

### 2.3 純粋な射影と実行admission

sourceからのprogram/interface/code/edge生成は、実際のcredentialを持たない段階でも調べられる。生成物は実行権限ではない。実際のadmissionとuseでは、現在のpolicyと根拠を検査する。

これにより、開発者は権限なしでも構造や未解決義務を理解でき、管理者はコードを勝手に書き換えずに許可を決められる。内部記録の閲覧は別の情報公開policyに従う。

### 2.4 実装と理論の責任を逆流させない

通信adapterの制約をCoreの正しさとして定義しない。逆に、意味上要求した原子性やfenceを「下位が実現する」とだけ書いて済ませない。各adapterの入口で、何の版・権限・scopeを保持し、どのstepで検査/確定/記録するかを明示する。

## 3. 研究と実装の依存順

以下のWは作業単位案であり、既存T/Iの新しい公式phaseではない。各作業は文書だけのclosed宣言を認めない。

| 単位 | 主対象 | 先行条件 | 主な成果 |
|---|---|---|---|
| W1 | 基礎の形式化と独立確認 | 要件表とF0.3の選択範囲を照合 | support/policy/currentness/OCC/観測の機械化、反例、前提台帳 |
| W2 | 通常の表現と型・証拠境界 | W1の識別・現在性・境界判断 | 最小の高階/handle/refinement規則、宣言的体系とchecker対応 |
| W3 | 参加・存在・patch・関係の統合 | W1, W2の必要部分 | 動的instanceの追加/撤去/更新と全グラフ保存 |
| W4 | 分散実行への意味保存 | W1/W3の使用点と線形化点、I3-3成果 | 実Rust/QUICへの対応、I3-4/5/6の不足を明示して接続 |
| W5 | 全成分の永続化と進化 | W3/W4、外部効果の採用profile | 実保存形式、全成分manifest、復旧・失効・patchの整合 |
| W6 | 秘密を含む観測と能動debugの分離 | W1、W3/W4の実trace、脅威モデル | 二実行保証、受動非干渉、資源境界、操作としてのdebug |
| W7 | 安全な参加環境とαの最小構築経路 | W2〜W6の採用範囲 | Mir内logic、View/FFI、継続参加、構築、SC-24の実統合 |
| W8 | 独立管理・公開・連合への拡張 | α受理とその契約 | 別管理主体と別版の接続、信頼翻訳、長期回収、WW要件 |

W5とW6の理論研究は依存境界があれば並行できる。すべてをW7のUI実装後まで待たせない。I3-4の実行例がW4の反例や仕様圧力に必要なら、限定して使えるが、F0.3の研究結果を自動採用してから動かす順序にはしない。

## 4. 各作業の具体的な完了条件

### W1：基礎を「紙の主張」から検査可能な成果へ

F3-01〜07、15〜18、20〜22を最初の機械化対象にする。式、rank certificate、policy evidence、type-sensitiveなκ、記録stamp、観測の消去を明確なデータとして定義し、証明対象にする。

単にPythonのif文を写すのではなく、宣言的な導出関係、checkerの健全性/完全性、遷移による保存を分ける。特に正しい導出をすべて落とすcheckerが通らないこと、証拠の型や対象が混ざらないことを否定例で示す。

**出口：** 機械検証のtoolchain/version・全コマンド・axiom/未証明の前提が明確で、少なくともsupport、policy/current-use、tracked validation、passive erasureについて一般の定義に対する証明を検査できる。手証明しかないものはそのまま残件にする。証明数ではなく対象範囲で判定する。

### W2：表現力を証明のために削りすぎない

少なくとも、通常の親への代入、他ownerのsnapshotを使う計算、再帰/反復、first-class handleによるmodule接続、局所理論の契約を持つ再利用関数を、最終構文に依存しない意味例で定める。

型規律の候補では、値環境Γ、資源環境Δ、場所/寿命/版の環境Ψ、効果rowと失敗row、残余義務を分ける。純粋な高階関数と、再開権を消費するeffect continuationは同じ複製可能な値にしない。

**出口：** 決めた正例がad-hoc helper無しに表現でき、宣言的な型付けに対するchecker/elaboratorの健全性と相対完全性が示される。依存型的な主張を局所導入する場合、外側の通常コードへの型消去・資源保護・証拠の版を説明する。少なくとも二つの異なる保証profileを同じboundaryで接続する。

任意の数学的に正しいprogramを自動認識することは出口条件にしない。契約を証明できる正例や必要なアノテーションは、その前に仕様として固定する。

### W3：全グラフと動的合成

定義とinstance、package依存とlive依存、関係DAGと状態の存在DAGを区別する。現在のtyped control APIで与えているlifecycle操作を、通常sourceのmodule/patch宣言とelaborationへ接続する。型付きcontrol APIがあることだけを、source-level構築言語の完成に数えない。F0.3の最小不動点とrank検査を、選択したhandleとmodule境界へ接続する。new/retire/reparentを、単なるrecord操作ではなくtyped lifecycle operationとする。

初期の推薦は、複数親をall/anyで明示し、未rootの循環は利用不能の診断とする方式である。DAG自身を保つべき関係は別に検査する。原子性を必要とする部分はscopeを公開し、global controlを暗黙に要求しない。

**出口：** A/B/Cの基礎構成へA/Cの追加構成を設置できる。依存先の退出、認可失効、code交換が、参照の現在性・fallback・証拠・進行中要求へ正しく伝わる。対応する正しい追加/交換/撤去が実際に受理され、全拒否ではない。

### W4：実分散への接続

既存I3-3の実通信成果を維持する。F0.3のDataを同じstructとして実装する必要はない。必要な観測関数と対応関係を定め、特に次を照合する。

| 意味上の境界 | 実装で示すこと |
|---|---|
| current context | request/contract/code/instance/memberの照合とtyped equality |
| use-time authorization | queue投入時だけでなくowner serve・結果release時の判定 |
| live support | retire/reparent/policy更新に対する派生状態の更新と古い利用の拒否 |
| state/decision commit | 応答喪失後も二度の状態変更を行わない記録 |
| generated site | helperやdeploymentが意味上の辺・結果を作っていないこと |
| observer projection | event内容・数・順序・redactionを出す根拠 |

**出口：** 実processとselected transportで、typed currentnessと失効/退役の順序を検査できる。有限な実行証拠と一般的なrefinement証明を区別する。弱いメモリ順序、lock、queueへの前提を明示する。機密性を移す場合は、単一trace保存だけで代用しない。

### W5：保存と更新の実現

snapshotの意味を先に区別する。推薦は、(a)現在の確定状態へ戻るsame-instance recovery、(b)現在権限を再受理するfresh import、(c)隔離された過去の検査、を別の操作として提示すること。用途に応じて初期profileを選ぶ。

same-instance recoveryは、現在headをsnapshot提出者と独立に確立する必要がある。実装は完全imageでもlogでもよいが、全component、未完了効果、patch状態、証拠依存、消費記録を覆うこと。未対応componentがあれば、保存を成功と呼ばない。

**出口：** process終了・再起動を含む実経路で、権限失効・退役・pending・prepared状態の前後を再現し、double mutation/古い使用の復活を拒否する。backupや失効記録が丸ごと過去へ戻る脅威を、hashを付けたことだけで解決したとしない。

二相コミット型patchを採る場合は、準備済みの権限を予約するのか、commit時の現在権限へ再照合するのかを統一する。安全性と可用性を別々に宣言する。

### W6：観測・デバッグと秘密

初期の推薦は、静的labelで値・構造・policy情報を保護し、権限失効は今後のreleaseを止める方式である。過去に見た情報を消したことにしない。秘密に応じたpolicy自体の変更やdeclassificationは別の契約とする。

**出口：** 低入力が同じ二実行について、private値やhigh処理の違いが、許されない値・存在・失敗・件数へ現れないprofileを定義・証明する。観測有無の消去比較と、秘密値を変える比較を別試験にする。buffer/queue/CPUの資源を分離し、過剰観測でdomainを止めない条件を測定する。

breakpoint、巻戻し、状態書換えは認可されたcontrol operationである。受動観測の定理をそのまま適用せず、何を停止・再実行するかを明示する。

### W7：αの利用能力

普通のMir sourceから、構築・参加・操作・関係・観測・追加/交換/撤去・保存/復旧が一つの経路になることを受理する。特定のゲームやWorldをCoreへ追加して達成したとはしない。

**出口：** 要件表のα-1〜α-8の採用範囲について、別の作者が新しい構成を記述し、network越しに利用できる。SC-24は同じidentity/契約/状態を持つ実システム上で再現する。privateデータを使う観測比較、失効や退出の反例、host/FFIの迂回拒否を含む。

最初のrendererは一つでもよい。継続構築のUIがCLIかGUIかは能力の問題と分ける。ただし、内部runtimeの呼出しを作者が手順ごとに手で組み立てることを、完成した構築入口としない。

### W8：遠期の開放性

独立管理者、複数の信頼域、版違いの接続、識別と参照、公開/発見、持続するlink、長期回収を扱う。ここではWWW全体を一つの閉じたMir programとして再コンパイルする前提を置かない。

**出口：** 別々に管理・更新した二つの構成が、内部source全体を共有せず、契約と必要な証拠/認可の下で接続できる。片側の更新が他方の同時更新を暗黙要求しない。共通の基礎は、業務上のあらゆる内容の真偽を判定する役割ではない。

## 5. 方式選択をどう扱うか

| 論点 | 推薦または候補 | 選択に伴う制約 |
|---|---|---|
| 複数親 | 明示all/any、根拠は帰納的closure | arbitrary否定を同じ式へ入れない。 |
| 認可の合成 | 全必要条件を同じκで評価、anyは明示branch | 任意の主体変換/委譲は別契約。 |
| 型/証明拡張 | 共通契約へ証拠をexportし、小さな検査境界を置く | 任意checkerの成功boolを信用しない。 |
| 失効 | 使用時に現在性を確認 | 準備後予約とは両立条件を明示する。 |
| 影響範囲 | read traceとabsence/index versionを追跡 | 未記録scanでは保証できない。 |
| 観測 | 許可射影の後に保持、domainと資源を分離 | 物理時間ゼロは主張しない。 |
| 復元 | current-head recoveryとfresh importを分離 | 信頼できるheadがなければ現行権限の復活防止は別手段が必要。 |
| 数値/高速sample | 数学的モデルと有限精度実装を別に対応づける | Int64/float/誤差を文法の細部として扱わない。 |

これらは研究上の推奨であり、既にownerが最終採用した選択ではない。30の元のQは `DECISION_DISPOSITIONS.json` で維持する。

## 6. 移植の順序と変更を受理する条件

第一に、F0.3のcontrol識別・policy evidence・support certificate・component registryを、既存のどのcarrier/検査点へ対応づけるかを記述する。実装を先に変更してから、意味を合わせない。

第二に、I3-3の受理済みの経路に対し、新しい使用条件が必要なprofileだけを明示的に追加する。旧sourceの意味を黙って変えない。新profileを実行できない経路は、義務を消すのでなく拒否する。

第三に、実行と失敗の両方でsource/Core/artifact/実occurrenceの対応を確認する。derived live集合やobserver viewから権限を再生成する経路は作らない。

第四に、目的の新例を普通のsourceで追加できることを確認する。試験helperに期待値やoperation固有の分岐を入れた場合は、その成果を一般的な言語能力として数えない。

第五に、正しい変更を拒否しすぎないかを確認する。保守的な拒否が初期profileに必要でも、拒否理由、必要な注釈、次に広げる条件を明示する。

## 7. 完了をどこで宣言するか

「この基礎については次の実装に依存してよい」と言うための最低条件は、対象の宣言的意味、受理アルゴリズム、量化された保証、代表的な正例、反例、TCB、実装との接続義務がそろっていることである。

F0.3はこのうち、選択したcontrol/現在性profileの定義・手証明・実行反例・接続条件を揃えた。未達なのは、必要な機械化、全体の表現力、使用する実装のrefinement、追加profileの秘密/進行/保存の保証である。

既存のI3-4へすぐ進むか、W1/W2の一部を先に閉じるかは、次の実装が何を前提とするかで決める。全一般理論が完成するまで何も実験しない方式でも、実装件数だけを増やす方式でもない。

## 8. 研究運営

一つの研究課題には、目的に結びついた反例、候補となる定義、証明すべき命題、現在の証拠、未解消の前提を対応づける。作者と最終受理の根拠は分ける。同じAIがコードと証明を書いたことは独立確認ではない。

研究結果のIDは公式THM/OBLを上書きしない。新しい定理を既存台帳へ取り込む場合、対象の定義と量化範囲を比較した上で、どの義務を実際に解消するかを別に判断する。

カレンダー上の日付や所要時間の数字を、未計測の研究の完了保証として置かない。完了時点は上記の能力と証拠で定義する。最終目標は、その判断を選別する基準として維持する。
