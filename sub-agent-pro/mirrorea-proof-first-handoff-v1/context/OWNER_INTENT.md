# 依頼者の意図と、消してはいけない条件

## 1. 中心目標

分散システムの内部について、通信APIを先に決め、その後に同じ意味を各ノードへ手作業で書き直す負担を避けたい。実行場所の情報を持つ意味のある一塊のコードから、各ノードのコードと必要な通信を導く。意味上必要な選択は少量の宣言・annotationへ置き、送受信・ID・再送・witness等の機構は通常のソースへ過剰に露出させない。

読みは依存、書込みは出来事という出発点を保持する。「透過的」とは遠隔性・遅延・失敗・権限を無かったことにする意味ではない。普通の親への代入等が、正しく検査・展開され、成立しなければ元の意図へ戻して説明されることが必要である。

並列処理、Webサービス、シンクライアント、対等な分散サーバ、VR、SNSへ同じ原則を適用したい。これは完成品を同時に全部作る依頼ではない。異なる利用領域で同じ構成原理が通用することを試す。

## 2. 遠期とα

最終に近い目標は、主体が抽象的な仮想空間の対象へ作用し、制御・検証された同期／非同期の計算環境を継続的に構成する、WWWを置換・再定義し得る基盤である。仮想空間は3Dに限定しない。

プログラムはpatchを通じて将来未知の構成を受け入れ、進化しながら使い続ける。初期時点に全参加者・全用途を列挙することを基礎の前提にしない。無限の同時資源、任意変更の無条件受理、任意partition下の可用性までは要求していない。

一旦のαは、通常のMir sourceからネットワーク越しに構築・参加・操作し、正しく観測・デバッグし、対応範囲内の追加・変更・撤去と保存・復旧を使える一つの利用経路。rendererだけ、固定デモだけ、別々のhelperの出力を結合したものはαではない。

## 3. 本来の特徴

状態の存在・寿命はシステム全体として親子または独立性を持つ。短命な他対象を参照する場合、契約に従うfallbackによってより存続する側へつなぐ。先祖であることは通信可能性・権限・同じ型の代替可能性を自動保証しない。live handleと歴史的引用は別である。

存在DAG、参加/admissionの依存、patch/moduleの依存、関係の計算DAG、出来事の因果関係を区別する。物理network、関数再帰、制御flow、一般の相互参照を一律DAGにしない。個別DAGだけでなく、退出・変更で他の依存がどう変わるかを扱う。

A/B/Cに展開した基礎構成へ、A/Cを使う新しい構成をpatchとして追加して参加する、という使い方がある。World/Avatarという名前は説明用であり、Core primitiveではない。静的合成と、状態・履歴を持つ動的合成の共通原理が必要である。

型システムでは、module/regionごとに必要な理論をlibraryのように導入し、異なる理論を使うコードを契約で接続したい。refinement、依存型的仕様、様相、資源所有、モデル検査、定理証明を必要に応じて使い分ける。全利用者に巨大な理論を強制しない。任意solverの成功boolを信頼するpluginでもない。

認証・認可は別の層である。複数の認証／policy層を着脱でき、それらにも形式保証を付けたい。型の証明を権限発行と混同しない。issuerを誰が信頼するか、失効、委譲、同一文脈への束縛は独立に扱う。

Mirのbrowser的な参加環境とheadless実行がある。基本計算・domain logicはMir内で記述し、Viewや外部計算はtyped FFI/provider境界へ出す。Unity/Unreal等の最終選択や全engine対応は未指定。外部engineへゲーム意味を隠して達成扱いしない。

Algebraic Effects的な内部構造は候補であり、一般の操作・継続・handlerの意味を持つ必要がある。OS的解釈は補助であって、OSそのものを完成させる依頼ではない。

save/loadはcut・要求・結果・継続・権限・fallback・patch・証拠を含む。Z-path/Z-cycleに関するcheckpointの数学と、実systemが完全な依存を集める責任を分ける。

可視化は忠実性、受動観測が意味を変えないこと、機密性、資源影響を分ける。breakpoint・書換え・巻戻しは別の認可された制御操作。readonlyだけで全部保証したことにしない。

## 4. 好みではなく維持すべき姿勢

表現力と使いやすさを、証明を簡単にするために失わない。健全性と相対完全性を適切な範囲で示す。有限なprofileは許せるが、それを原理上の永久制限へ昇格させない。

理論のための限定実装は許すが、未確立な基礎を既成事実にして製品実装を拡大しない。正しい理論が目的に適しているかも検討する。体系を短くするために必要な意味の区別を消さない。

PrismCascade、Typed-Effect Wiring Platform、Reversed Libraryは独立した接続先・具体物。全て同時に完成させる追加scopeではない。World-Webの遠期目標は、今の設計が将来を閉ざさないかを判断する基準である。

## 5. 直近の運用要求

主担当は一人。sub-agentは一切使わない。これは依頼者の運用制約であり、特定モデルの不具合が外部検証済みという主張ではない。

oracleを単発・文脈なしの助言者として利用してよい。質問ごとに目的、規範、現状、コード／定義、前提、争点を渡す。待機はおおむね180秒間隔とし、遅いことだけで中断・再送しない。時間ではなく、回答完了・実エラー・安全条件で判定する。

ここまでの話を知っている前提で作業しない。要件表と本briefにない世界観や不可逆な選択を勝手に補わない。必要なら最小の確認事項と選択肢・影響を示す。一方、通常の調査・証明・可逆な技術比較のたびに作業を返さない。
