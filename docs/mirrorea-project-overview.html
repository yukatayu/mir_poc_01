01 / 目的

目標像: 利用者からは「一つのプログラム」、実行時には「検証された分散システム」

最終的に利用者は、World、Room、Avatar、ゲームなどを Mir のライブラリや自分の型として定義します。これらは言語の組込み概念ではありません。Mir は、どこで処理すべきか、必要な権限・失敗・通信・観測を明示化するための最小の意味論コアです。

  1. 1. Mir を書く通常の代入、読み取り、状態、when を用いてドメインを表す。
  2. →
  3. 2. 隠れた結果を出す所有者宛 request、effect / failure、権限・witness 義務、publish / observe を明示化する。
  4. →
  5. 3. 検査して動かす型・契約・残余義務を検査し、verdict 済み Core だけを実行する。
  6. →
  7. 4. locus ごとに導出するCore と topology から、各実行場所向けの成果物と通信境界を得る。
  8. →
  9. 5. 観測・進化するredaction 付きの occurrence evidence を観測し、patch を検査して activation cut で有効化する。

設計の中心原理

  • 通信 API を先に固定せず、検証済みの意味から導出する。
  • 表層コードをイベント駆動の記述で埋めない。読みは依存、書きは出来事として Core / Trace 側に現す。
  • elaboration が生成する capability / witness 義務と request edge は隠さず明示し、authority 自体は新規に創出しない。
  • 認証・認可・membership・capability を transport metadata に押し込まない。

目標だが、まだ宣言しないこと

  • 一般公開サービス、WAN federation、分散耐久保存、最終 ABI / SDK。
  • 任意 native / WASM provider の実行や、単一ゲームエンジンへの固定。
  • 実験があることをもって、公式の言語実装・定理証明・適合性達成と呼ぶこと。

02 / 構成と理論

Mir / Mirrorea と外部境界を分け、意味を保って層を越える

これは部品の完成度の図ではなく、責務の境界図です。下の層の都合を上の層の意味にせず、上のドメイン語彙を下の primitive にしないことが、置換可能性と検証可能性を守ります。

S0

Surface: 通常のソース

代入、読み、状態宣言、when、join。利用者が主に触る層。

Mir
S1

Core: 明示化された計算

owner-directed request、effect / failure row、capability / witness 義務、source span。

Mir
S2

Trace: 履歴と cut

occurrence DAG、因果順序、atomic_cut、save/load、devtools の根拠行。

Mir の意味層。実現は Mir / Mirrorea 境界にまたがり得る
S3

Verify: 検査・モデル・証明

decidable checker、model check、Lean、診断。三線を区別し、未解決義務を明示する。

Mir の横断検証層
S4

Projection / Fabric: locus ごとの導出

Core と topology から per-locus 成果物と通信境界を導き、typed Provider / View 境界へ接続する。

主に Mirrorea
S5

Domain: 利用者の世界

World、Room、Avatar、ゲーム、協調エディタなど。ライブラリ・アプリケーションとして定義する。

利用者定義。Mir core primitive ではない
(S6)

Provider / View 境界と Host

Provider / View は typed seam、Host は OS / browser / engine / FFI 先です。意味の owner ではなく、BND-007 を越えて接続します。

外部境界。Provider / View と Host を同一視しない

必ず越えない境界

Surface から Core への elaboration は、必要な request edge と capability / witness obligation を生成し得ますが、それらを隠しません。source span と effect / failure row を保存し、authority を新規に創出しません。runtime は verdict 済み Core だけを fail-closed で動かします。

別物として保つ衛星系

Mir、Mirrorea、PrismCascade、Typed-Effect Wiring Platform は関連しますが、単一実装に融合する前提ではありません。後二者は Canon 上の独立衛星であり、exact な層配置・統合関係・実装責務はこの図では選びません。

理論が追う四つのグラフ

出来事 DAG

write、send / receive、publish / observe、grant / use、admission、activation、cut の因果順序。逆向きの隠れ辺を持たない。

状態・存在 DAG

状態セルの親子依存、寿命、lease、fallback lineage。失効時は暗黙復帰でなく単調劣化する。

locus / admission グラフ

locus、participant、membership epoch、incarnation、role claim と capability grant の区別を保つ。

patch・overlay DAG

source patch、互換性、activation cut、patch 間依存。hot-plug は最後に載せる capstone。

admission や activation は occurrence DAG 上にも出来事を持ち得ますが、membership / incarnation の構造は locus / admission graph、patch 依存と互換性は patch / overlay DAG に属します。同じ操作名が現れても、四つの graph の node や relation は同一ではありません。

層を越える BND 契約の抜粋

BND-001 Surface → Core隠れ辺なし。span と row を保存し、決定的に obligation を明示化し、authority を創出しない。
BND-002 Core → Checker未処理義務は ResidualObligation として残し、hidden success を禁止する。
BND-003 Checker → Prover / ModelCheckerstatic / model-check / proof を分離し、model-check の結果を一般証明と呼び替えない。
BND-004 Core → Runtimeverdict 済み Core だけを fail-closed で実行する。
BND-005 Runtime → Transporttransport は配送のみ。authority を metadata に潰さない。
BND-006 Runtime → Projectionownership、read/write dependency、effect/failure row、capability/witness、visibility/redaction/retention、fallback lineage、cut/save-load、span を保存する。
BND-007 Projection → Viewprovider は semantic owner ではなく、View に game logic を置かない。
BND-008 Runtime → DevtoolsH（occurrence history / Trace の正規履歴）由来の typed evidence、redaction、retention を守る。
BND-009 Canon → LABCanon が規範、LAB は evidence。逆向きの暗黙昇格を禁止する。

四つのグラフは別のものです。participant を Place と同一視する、patch を出来事列に潰す、transport を authority とみなす、といった混同を防ぐことが理論の役目です。
