01 / North Star

通信 API を先に設計せず、検査済みの意味から通信を導く

通常の分散システム開発では、RPC、message schema、service boundary を早い段階で固定しがちです。Mir の起点は逆です。利用者は一つの意味あるプログラムを書き、言語処理系が owner、locus、dependency、authority、effect、failure、lifetime、observation を検査した後で、各 locus の処理と通信境界を射影します。

変えてはいけない設計軸

  • World、Room、Avatar、Game は利用者の domain/library 語彙で、Core primitive ではない。
  • Surface intent、Core operation、runtime occurrence、domain event、observation row は別物。
  • 評価場所は権限ではない。認証 evidence も、それだけでは mutation authority ではない。
  • 通信、失敗、effect、authority、information release を隠さない。
  • patch は eval ではなく、検査・互換性・admission・activation cut を通る。

長期像に含めるが、現在は主張しないもの

  • WAN、federation、distributed durable save/load、global exactly-once。
  • production identity provider、一般公開運用、scale / performance 保証。
  • 最終 public grammar、API、ABI、wire format、renderer/engine integration。
  • 任意 relation DAG / label lattice / dependent type theory の一般定理。
  • PrismCascade や Typed-Effect Wiring Platform を Mir runtime に統合し切ること。

02 / Current position

現在地は「Theory T1」「official I2 exit」「program closed」の三座標で読む

M0–M10 は閉じた ADR-0015 program、SYS-0--SYS-7 は閉じた ADR-0026 program、T0–T2 / I1–I6 は長期 lifecycle です。bounded program の完了をTheoryやbroad Phase、後続I3の自動activationと読み替えないことが最重要点です。下の lifecycle / program 表は、独立した三軸を補足する状態座標です。

独立した三軸 — many-to-many の責任 map

semantic strata（S0–S6） は意味の責任、project/product layers（PL-0–PL-6） は製品積層の責任、lifecycle / implementation phases（T0–T2 / I1–I6） は実現・受理の状態を表します。三軸は多対多で、同じ番号や完了語から相互の受理を導きません。

Canonical project/product layer map に、PL-0 Host / physical substrate、PL-1 Mir language and semantic kernel、PL-2 Mirrorea distributed fabric、PL-3 Mir Browser / Host safe participant runtime、PL-4 Shared-Space / World-Web platform、PL-5 Domain Kits and applications、PL-6 Reversed Library / knowledge-world projectを定義しています。PL-4は責任境界のみで、Reversed LibraryはMirroreaのcompletion条件へ混ぜない。PrismCascadeとTyped-Effect Wiring Platformはsatelliteとして保持します。

Browser/Host trust boundary contract と cross-edge security invariants は trust tier T0–T4 を Theory T0–T2 とは別に定義します。T1 checked untrusted Mir package の package admission と semantic grant は分離され、raw FFI / direct store は許可されません。Runtime/Projection→View は redaction 済みの projection を渡し、View は authoritative domain semantics を所有せず presentation-local computation のみを行います。

05 / Two views of “what works”

エンドユーザー視点と、言語・理論視点を同じ段階で照合する

現在の reference system は、利用者に「普通のコード」を見せながら、下流で分散意味を明示するという設計を実証しています。ただし対象 grammar と runtime profile は有限で、外部開発者向けの安定 product ではありません。

1. same-owner RMW — 普通の代入

Role[self] at BrowserClient {
  when attack(target: Player) fails (...) {
    at World {
      player[target].hp =
        player[target].hp - player[self].atk
    }
  }
}

利用者: attack を普通に書く。
理論: authority origin は caller、evaluation site は owner。owner service 時に same-owner RMW として 100→90→80。

2. designated evaluator — 値を決定

designated evaluate Evaluator
  on tick attack_tick
  publish result =
    player[self].atk + 1

利用者: authoritative decision と時計だけを書く。
理論: evaluator、trigger、input/result frontier、version、policy stamp を保持し、consumer は semantic value を再評価しない。

3. maintained relation — 関係を配る

relation bird_follow at World {
  subject bird: Player
  primary perch_anchor epoch primary_epoch
    transform translate(3, -2)
  fallback nest_anchor epoch fallback_epoch
    transform identity
  publish relation
  project at Viewer local
}

利用者: follow/fallback 関係を書く。
理論: owner-held relation を consumer へ射影し、同じ presentation context で局所評価。毎 frame の絶対 pose stream を意味の正本にしない。

06 / Language and theory

有限 Theory v0 は閉じたが、一般 metatheory は意図的に残している

Theory v0 の重要な成果は、機能別の toy model を並べるのではなく、Surface、Core、Config、Step、WellFormed、Trace、Projection、Diagnostic を一つの有限 proof-facing universe に置いたことです。一方、有限な theorem を任意 program/topology の一般証明へ言い換えていません。

model-checked-bounded3OBL-028, 033, 058。有限 state/target enumeration。
runtime-monitored5OBL-034, 057, 059–061。有限な実装/fixture correspondence。

現在 lean-stated の ledger row はありません。M3–M9 の七つの foundation は Lean 4.29.1 で --trust=0 compile 済みですが、依存する propext と一部 Quot.sound は明示されており、「すべて axiom-free」とは主張しません。

評価を五つの直交軸で持つ

  • semantic form
  • evaluation site
  • trigger / clock
  • authority origin
  • materialization

配置を権限と混同せず、owner / designated evaluator / consumer / provider を同じ calculus で説明します。

値と関係を使い分ける

designated evaluator は semantic value を authoritative に versioned materialize。maintained relation は関係を source of truth とし、consumer で late materialization。二方式を一つへ潰しません。

二つの fallback を分ける

semantic fallback は existence/lease/authority/lineage の失効で単調に進み、復帰は fresh reacquire。presentation fallback は packet gap/latency/LOD で、semantic state を変えません。

authority chain を明示する

credential → principal claim → admission/policy → capability grant → validated use。role、key、locus、transport session、signature 単独を authority と呼びません。

runtime layer と verifier を分ける

auth/policy は Contract → Contract。verifier は Judgment/Obligation → Evidence/Diagnostic/Residual。verifier は capability を発行せず、failure や effect を消しません。

保存と進化を意味状態として扱う

save/load は byte copy ではなく validated cut。patch は parse/check/elaborate/compatibility/admission/verdict/activation の pipeline。stale resurrection と rejected mutation を禁止します。

今回の研究で収束した重要な知見

Authority is not placement

「S で計算する」ことと「S の authority を持つ」ことは別です。この分離を Core consequence、runtime validation、trace まで保つことで、generated distributed program が ambient authority を密輸するのを防げます。

Relation-first late projection

derived value stream を上流で毎 frame 固定せず、owner-held relation と binding lineage を配り、consumer が同一 presentation context で評価する方が、相対 coherence・privacy・fallback の意味を保ちやすいことが有限 slice で確認されました。
